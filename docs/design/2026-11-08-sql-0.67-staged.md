# apitap.sql() 0.67: staged plans — every TPC-H query

Status 2026-11-08: design; leg `benchmarks/e2e_sql_tpch.py` (all 22 queries, DuckDB's
text, sf 0.01, customer/lineitem/partsupp on Postgres, the rest on MySQL) gives
13 OK, 0 wrong, 9 refused: Q2 Q11 Q13 Q15 Q16 Q17 Q20 Q21 Q22.

## The idea

The 0.66 engine answers one SELECT shape (a join of up to N tables, GROUP BY,
aggregates, semi-joins, ORDER BY, LIMIT). Every refused query is that shape
applied more than once: a subquery answered first and used by the outer query.
So 0.67 adds no second engine. It splits a query into **stages**, each a
SELECT the 0.66 engine answers, and keeps each stage's answer in memory as a
table the later stages read like any source (`mem://<run>/<stage>`). The
source servers still only scan and send ([[no-heavy-pushdown]]): every join,
semi-join and aggregate between stages is apitap's.

A stage's answer is small by construction (an aggregate's groups, a key set);
a stage that would be large is narrowed first by the outer query's own
filters (the "magic set": the correlation key restricted to the outer table's
filtered keys, as an `IN (SELECT …)` semi-join apitap evaluates).

## Rewrites (in order of application, recursive)

| # | Shape | Rewrite | Queries |
|---|---|---|---|
| R1 | `WITH name AS (q)` | stage q as `name` | Q15 |
| R2 | derived table the flattener refuses (GROUP BY / HAVING / DISTINCT inside, joined, column aliases) | stage it | Q13 Q22 |
| R3 | uncorrelated scalar subquery | stage, one value → literal | Q11 Q15 Q22 |
| R4 | outer HAVING | stage the grouping (HAVING's aggregates as hidden columns), filter the stage | Q11 |
| R5 | SELECT without aggregates | GROUP BY every output + hidden COUNT(*), rows repeated by it after the engine | Q2 Q15 Q20 Q22-inner |
| R6 | COUNT(DISTINCT x) GROUP BY g | stage GROUP BY g, x (x not NULL); COUNT(*) GROUP BY g over it | Q16 |
| R7 | `IN (subquery)` the semi-join refuses | stage the subquery, semi-join on the stage | Q20 |
| R8 | correlated scalar subquery, equality correlation | stage `GROUP BY corr keys` (narrowed by the outer table's filters), join it, compare | Q2 Q17 Q20 |
| R9 | `LEFT JOIN … ON` + GROUP BY | inner join ∪ anti-join (`NOT EXISTS`) with NULLs | Q13 |
| R10 | `[NOT] EXISTS` with an inequality correlation (`l2.c <> l1.c`) | stage MIN(c), MAX(c) per key; the inequality becomes a compare with them | Q21 |

Engine additions the rewrites need: a `mem://` source (schema, row count,
projected batches); `SUBSTRING` as a computed column (like `EXTRACT(YEAR)`);
conditions across two tables evaluated per joined row where one side's value
is a looked-up dimension payload (R8, R10).

## Order of work

1. `mem://` source + stage runner, R1 R3 R4 R5 R6 R7 (Q11 Q15 Q16) + SUBSTRING (Q22).
2. R9 LEFT JOIN (Q13).
3. R8 + cross-table row conditions (Q17 Q2 Q20).
4. R10 (Q21).
5. SF10 numbers in the cage for the new queries, live views over 3+ tables, PGO training of sql().

Each step: the leg goes RED→GREEN for its queries, the 13 passing queries stay exact.

The four OOMs are one cause: a GROUP BY of millions of groups held in memory
(Q11 2.1M `ps_partkey`, Q13 9.9M `c_custkey`, Q16 (brand, type, size,
suppkey), Q21's magic set of order keys). Measured on Q11's grouping alone:
the probe-side groups (`cgroups`) cost ~60 B a group with their accumulators,
and the finalize copies them whole up to three times (`combine`, `strip`,
`collate`), each a new `Groups` beside the old.

Fixes, in order:

1. Done: HAVING in the engine (`aggregate op number`, exact on decimals,
   applied in `order_rows`): a staged grouping keeps only its passing groups.
   `result()` fills only the vector of each column's kind (it filled five a
   cell). Group keys in one arena (`KeyArena`), not a box each.
2. External GROUP BY: past the group budget, the partial groups (key,
   accumulators) are written to N files by a hash of the **final** key and
   the table cleared; at the end each file is merged alone (combine, strip,
   collate, HAVING) and its rows appended, so the peak is one partition. ORDER
   BY then sorts the answer rows (a stage has none; LIMIT keeps its top-N
   across partitions).
3. Stages on disk: a stage past a byte budget is written as Arrow IPC to the
   run's temp directory and read back streaming (`mem://` keeps the small
   ones in memory), so Q13's 9.9M-row stage never sits in RAM whole.
