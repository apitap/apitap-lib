### Scenarios and verifier reasoning

**N1 (P1) D10 fix ignores the journal that 0.62.0 left: a Rekey cut between its DELETE and INSERT is silently skipped on the replay, so the row is lost**  
pg->ch log_based (replica) on 0.62.0. A window holds a TOAST re-key (UPDATE t SET id=9 WHERE id=1, with the TOASTed column unchanged), so ResidueOp::Rekey has missing cells. 0.62.0 journals the image under '1|"id" = 1' (ver = window end), deletes the old key, then the run dies (SIGTERM from the upgrade, OOM, a lost connection) before the INSERT at key 9. The operator installs 0.62.1. The replay sees journal_live = true (the old row has ver > start), but jkey now builds 'pos|1|"id" = 1', so journal_get misses. The readback at the old key returns nothing (0.62.0 already deleted it), and the None arm does `continue`. The row is never inserted at id=9, the watermark commits, and the row is gone from the destination with no error. A MaskedUpdate cut the same way fails 'row missing ... not in the residue journal' on every rerun: the lane is stuck until someone re-bootstraps by hand. The release note promises a stop for every case, but the Rekey case is silent.

Evidence: dest_ch.rs:993-998: jkey now formats "{pos}|{n}|{pred}". In fdb51a3 the old format was "{n}|{pred}", and 0.62.0 rows are never consulted. dest_ch.rs:1138-1160: replay && !missing -> journal_get(new key) -> miss. dest_ch.rs:1170-1197: readback at old_pred; `None => continue` with the comment 'an attempt from before the journal existed already moved the row', which is false when the journal exists in the old format. 0.62.0 Rekey order (fdb51a3 diff): journal_put -> delete_owned(old_pred) -> delete new_pred -> insert, so a cut after the first delete leaves neither key. docs/review/2026-10-20-release-0.62.1.md:37-40 claims 'the run stops'. The first replay after the upgrade still starts at the dead attempt's S, so the old window-ordinal key 'n|pred' would be valid for it as a fallback.

- verifier (code-path, UPHELD, P1): I re-derived the path at HEAD and it holds end to end. 0.62.0 (884c3a0) keyed a journal entry as "{n}|{pred}" with ver = id.end(). Its Rekey ran in this order: journal_put, delete old_pred, delete new_pred, insert. A cut after the first delete therefore leaves the row at neither key. Only the journal entry survives, under the old key format.

On 0.62.1 the rerun starts at the same window start S, because the watermark was never committed.
- journal_live counts any row with ver > S. The 0.62.0 row has ver = old end > S, so replay = true. The sweep in journal_put only drops rows with ver <= S, so it does not remove that row.
- jkey now builds "{pos}|{n}|{pred}". journal_get filters on exact k equality, so it misses.
- The code then falls through to the readback at old_pred, which returns no row because 0.62.0 already deleted it.
- The Rekey match arm `None => continue` is unconditional. It does not look at `replay` or at the journal at all. The op is skipped, nothing is inserted at the new key, and the window commits. The row is silently lost.

The insert-only variant is lost the same way: the readback uses FINAL with _apitap_deleted = 0, and the old row has already been deleted. MaskedUpdate in the same situation errors instead, which is the stop the release note describes. The note's promise that "the run stops" is false for Rekey.

There is no migration, legacy-key fallback or old-format detection anywhere in dest_ch.rs at HEAD. The WIP diff to dest_ch.rs only removes a duplicate `dbg` let and does not change this.

This is not a re-report. M-12 (CH) was closed by the 0.62.0 journal, and the M-12 entry itself says "Never continue silently". The D10 key-format change reopens that loss for any journal left by 0.62.0, so it falls under exception (a): a fix for a known item that introduced a regression. I keep P1 rather than P0. The loss is silent, but it needs a narrow trigger: a 0.62.0 crash between a TOAST Rekey's DELETE and INSERT, followed by an upgrade before the rerun.
- verifier (reachability, UPHELD, P1): I traced the path end to end at HEAD and it holds. 0.62.0 (884c3a0) keyed journal rows as `{n}|{pred}`, with ver = the window end. For a Rekey it ran journal_put, then deleted the old key, then deleted the new key, then inserted, and each step is a separate HTTP exec. So a cut after the first DELETE leaves the row at neither key.

On 0.62.1, journal_live() asks only whether some row for this table has `ver > start`. The 0.62.0 row has ver = the old window end, which is above start, so replay = true. jkey() now builds `{pos}|{n}|{pred}`, and journal_get matches on k exactly, so the lookup misses. The code then reads the old key back. It was already deleted, and on insert-only tables the FINAL ... _apitap_deleted=0 filter returns nothing too. The `None => continue` arm drops the op: nothing is inserted at the new key, no error is raised, and the window commits. That is a silent lost row, while the 0.62.1 release note promises "the run stops" for this case. That promise only holds for MaskedUpdate, whose None arm returns an Err.

This is not a duplicate. M-12 and M-13 were closed for CH by the journal in 0.62.0, and D10's fix added this upgrade-path regression, so it falls under exception (a): the fix ignores state the previous release persisted.

Reachability: pg->ch log_based with a TOAST re-key is a supported path, and PG re-streams the same Rekey from confirmed_flush on the replay. No gate leg covers 0.62.0->0.62.1. The rolling-upgrade legs are 0.55.1 and 0.56.0, and e2e_ch_journal_window.py exercises MaskedUpdate on one build only.

Why P1 and not P0: the exposure is narrow. The journal shipped only in 0.62.0, and that release was live for about 9 hours (08:36 to 17:38 on 2026-10-20). The loss also needs a crash at an exact instant, between the old-key DELETE and the INSERT, followed by an upgrade before a successful rerun. The data loss is silent, but it takes a crash at the right moment plus a version change, not normal input alone.

The suggested fallback is sound. On a miss, try the legacy `{n}|{pred}` key, which is valid for the first replay because it starts at the dead attempt's S. Alternatively, make the Rekey `None` arm return an Err whenever replay is true. Either one also turns the MaskedUpdate case from a stuck lane into a recovery.

The WIP diff in dest_ch.rs removes one line (the None arm moves to line 1196) and does not change this.

**N2 (P1) D9 fix moves a table that 0.62.x already filled with tombstones to the general path, whose masked readback (no FINAL) picks an arbitrary stale version**  
A table bootstrapped on 0.62.1 with engine='ReplacingMergeTree(_apitap_ver, _apitap_deleted)' and order_by='tenant_id, id' (PK id) ran on the tombstone path. Every update of id=7 (tenant unchanged) inserted a new version at (42,7), and under FINAL that was correct; the old masked readback also used FINAL. After upgrading to HEAD, insert_only_for returns false, so the general path runs. The next window has UPDATE t SET small='x' WHERE id=7 with the TOASTed column unchanged, which is a MaskedUpdate residue. The readback is `SELECT big FROM t WHERE "id" = 7` with no FINAL and no ORDER BY. Before a background merge, it returns several versions in arbitrary part order, and lines().next() can be an older version. The patched row is inserted with the old TOAST value after the key's rows are deleted, which silently reverts that column. A Rekey readback (line 1174) has the same defect. The rows D9 already damaged (a deleted id still visible, two rows after a tenant move) are never repaired, and the new progress note never says that a re-bootstrap is needed.

Evidence: dest_ch.rs:1682-1712: the verdict is shape && keyed, and when shape is true but the key differs it only emits a note. dest_ch.rs:1040-1053: the readback uses FINAL only when insert_only, so here it is a plain `SELECT ... WHERE {pred}` followed by body.lines().next(). dest_ch.rs:1172-1175 does the same for Rekey. The general path assumes one row per key, which holds only for tables it wrote from the start. Under 0.62.1 the tombstone path inserted one version per update with no DELETE (dest_ch.rs:862-890 insert-only branch). Not in a release yet: f579498 is not an ancestor of 0d8794d.

- verifier (code-path, UPHELD, P1): This is a new failure mode introduced by the D9 fix, not a re-report of D9. The fix (f579498) changed which path a table takes, but it did not account for data that 0.62.1 had already written to the table under the old path.

On 0.62.1, a table with engine ReplacingMergeTree(_apitap_ver, _apitap_deleted), ORDER BY (tenant_id, id) and key id took the tombstone path. That path writes a new row version for every update and never runs a DELETE. Two kinds of extra rows build up:
- older versions at (tenant, id) that stay until a background merge collapses them;
- tombstone rows at (DEFAULT, id) with _apitap_deleted=1, which a merge never collapses into the live row because their sorting key differs.

On 0.62.1 this history was harmless for keys whose tenant never changed, because the masked readback used `FINAL ... AND _apitap_deleted = 0` (0d8794d dest_ch.rs:1046 and 1169).

At HEAD, insert_only_for returns `shape && keyed`, so this table is now false and takes the general path. That path assumes one row per key. I found nothing that reconciles the history at the switch: no OPTIMIZE, no FINAL, no deleted-row filter in the general-path readbacks. The only change is a progress note saying the table now applies by delete-then-insert. It does not say a re-bootstrap is needed.

The bulk upsert and delete paths do clean a key, because their DELETE uses the key table and removes every version. A MaskedUpdate is different: it happens whenever a Postgres UPDATE leaves a TOASTed column unchanged, which is a normal case. When the first touch of a key after the upgrade is such an update, the general-path readback is a plain `SELECT ... WHERE pred` with no ORDER BY, and it takes `lines().next()`. That line can be an older unmerged version, or a tombstone row whose TOAST column holds the default value. The next steps are the residue journal_put, delete_owned(pred) and insert_owned, so the stale value is written back as the only row for that key. The TOAST column is silently reverted, and the residue journal stores the bad image too.

The Rekey readback has the same defect: it only adds FINAL when insert_only is true. The rows D9 had already damaged (a deleted id still visible, a key with two rows after a tenant move) are only repaired when a later bulk change touches that key.

I rate it P1, not P0, for three reasons:
- it only reaches tables that were on the D9 configuration on 0.62.x;
- each key is exposed once, at its first masked touch after the upgrade;
- f579498 is not in a release yet (`git merge-base --is-ancestor f579498 0d8794d` returns false), so a fix can land before the next release.

The uncommitted WIP diff to dest_ch.rs only removes a duplicate `let dbg` line and does not change this finding.
- verifier (reachability, UPHELD, P1): The fix for D9 (f579498, not yet released) is correct for a table that starts on HEAD. It is not correct for a table that 0.62.1 already wrote on the tombstone path. That is a new failure mode introduced by the fix, so this is not a duplicate of D9. Under 0.62.1, a table with engine='ReplacingMergeTree(_apitap_ver, _apitap_deleted)' and order_by='tenant_id, id' over key id took the insert-only path. A plain update of id=7 with the tenant unchanged inserted a new full version at (42,7) and issued no DELETE. Under FINAL that key was correct, because D9 only damaged deletes and tenant moves. After the upgrade, insert_only_for computes shape && keyed, which is false, so the unit runs the general path, and the general path assumes one row per key. The first time the upgraded run touches such a key through a PG MaskedUpdate (TOAST column unchanged) or a Rekey, the readback is a plain `SELECT big FROM t WHERE id=7` with no FINAL, no _apitap_deleted filter and no ORDER BY. The result is the first line of whatever order the parts come back in. While the old versions are not yet merged, which is normal for recent parts, and ReplacingMergeTree never promises a full merge, that line can be an older version. It can also be a D9 tombstone row (deleted=1, defaults in the columns), since nothing filters _apitap_deleted. The general path then deletes every row of the key and inserts the patched row carrying the stale TOAST value. That is a silent revert of a key that was correct before the upgrade. A key whose first post-upgrade touch is a bulk upsert or delete is safe, because the bulk path deletes by key first and leaves one row. So the exposure is limited to residue ops (masked update or rekey) that come before any bulk touch of the key, and only where the TOAST value differs between unmerged versions. The WIP diff in dest_ch.rs (one deleted line) does not touch this. The new leg e2e_ch_tombstone_sort_key bootstraps fresh on HEAD and checks only id/tenant_id under FINAL, so it covers neither the upgrade nor a masked update. No changelog or progress note tells the user to re-bootstrap.
