# 0.61.0 — the binary body: the CH CDC lane at +22%, and a read path without a pump

Two engine waves from the 3M/min design (`docs/design/2026-10-08-mesin-3jt-per-menit-zero-copy.md`):
L1b (the synchronous window scanner) and P4 (the RowBinary body), measured on the
heavy 30-table shape — 30 tables x 1M rows, 15 columns, `large_str` ~1KB, one
`apitap.transfer()` group, 256 MB / 0.5 CPU, pg→CH (ClickHouse 25.8).

## Measured results (heavy30 PREBUILD catch-up arms, 6M changes per arm)

| arm | rate | cap_frac | MEMPEAK |
|---|---|---|---|
| 0.60 baseline (sweep) | 24.6k/s | 0.69 | 89.6 MB |
| + L1b FrameScanner | 26.8 / 28.3k/s | 0.642 / 0.640 | 114 / 115 MB |
| + P4 RowBinary body (binary=1) | **30.2 / 29.8k/s** | **0.639 / 0.634** | 119 / 113 MB |

- **Cumulative: 24.6 → 30.0k/s (+22%)**, every arm 30/30 checksum MATCH, no OOM.
- L1b: rate +3.7% (noise edge) but cap_frac reproducibly −9% (0.70 → 0.64) — the
  syscall/allocation savings are real; kept as the P1/P2 foundation.
- P4: +15.1% rate, −14% cap_frac, both arms above both baselines (no overlap).

## What changed

| commit | change |
|---|---|
| `dad499a` | **L1b FrameScanner**: the CopyBoth read half becomes one owned 1 MiB window scanned synchronously — one `read_buf` per refill, frames are `split_to` slices (no per-frame allocation, no pump task, no channel); the half-open silence budget rides the refill (one timer per ~1 MiB, not per event); torture corpus: carry across refills, hostile lengths refused by the 1 GB cap, window growth, silent-stream timeout |
| `d1b2a4f` | **P4 RowBinary body**: a binary pgoutput stream keeps its send-format cells (no per-row text rebuild at decode); the apply resolves `(RbType, nullable)` from the PHYSICAL destination table's `DESCRIBE` plus pgoutput-OID conversion rules (jsonb version strip; bytea/arrays/unknown → whole-table TSV fallback); row + tombstone bodies render through `transcode_field` into `FORMAT RowBinary` |
| `b5af4e5` | every key path converts binary keys to text first (clear-phase key table, residue predicates, tombstone fallback) — the first A/B arm caught the leak via ClickHouse's parse error; a binary stream whose table has an unmapped column renders the row back to text instead of feeding binary bytes to the TSV parser |
| `1865088` | **`APITAP_PG_BINARY` becomes tri-state**: `1/true/on` forces binary on every lane, `0/off/false` forces it off, unset = **ON for ClickHouse destinations** (where the RowBinary body measured +15%) and text elsewhere (their renderers are text-native) |
| `d55ff64` | **reverted** the MySQL RowBinary twin (`e444393`): measured neutral on the string-heavy shape (mean +6% inside a wide noise band, cap_frac up — the text parse adds client CPU while the volume win is small when strings dominate), documented in §14.18 |

## Honesty notes

- The MySQL lane's catch-up ceiling is 25.6k/s @0.5 CPU (cap_frac 0.94 — it is
  CPU-bound, not body-bound); its RowBinary body format was measured and rejected.
  The next my-lane levers are per-change CPU work, not the body format.
- The post-P4 profiles are flat (no symbol above ~1.7%); the remaining path to
  3M/min at this cage is grinding 1–3% items (allocation family, key hashing,
  runtime overhead), plus the deeper P1/P2 zero-copy work.
- 0.60's headline 49.3k/s was the 2-table 460B-row shape; this release's numbers
  are the 30-table 1KB-row shape — the comparison in the table is like-for-like.
