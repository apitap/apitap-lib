0.64.0 carries the 33 commits since 0.63.0: the deep-review-3 fix wave

## Upgrade notes (read this one)

**MySQL → ClickHouse lanes bootstrapped on 0.62.x or earlier with a
Replacing-family engine** (`ReplacingMergeTree`, `ReplacingMergeTree(ver)`,
or the tombstone pair) and no `order_by=`: 0.62.x created the destination
`ORDER BY tuple()`, and the engine's own background merges have been
collapsing every row sharing that empty sorting key into one — the
destination silently holds a fraction of the source while every run stays
green. Nothing can repair the folded rows but a re-copy.

From 0.64.0 the drain **refuses** such a table on its first apply,
before any window, naming the repair:

    log_based: <t> is ReplacingMergeTree over ORDER BY tuple() — a bootstrap
    from 0.62.x or earlier left it unkeyed … Re-bootstrap <t> (clear its
    _apitap_state row and run again — with the engine= it was created with,
    if it had one), which rebuilds it ordered by its key

Plain `MergeTree` over `tuple()` collapses nothing and stays allowed; a
keyed collapsing engine is the D9 note's business. The leg
(`e2e_ch_legacy_tuple_engine.py`) rebuilds a bootstrapped destination into
the 0.62.x shape, watches the rebuild itself fold the table on the spot
(the damage, rig-proven), asserts the refusal with the window left
pending, and then executes the remedy for real — the folded row comes
back.

## The deep-review-3 wave (R1–R32)

The wave's own record is `2026-10-22-deep-review-3.md`; the shapes it
closed, in one line each:

- **MySQL CDC refuses the row-removing DDL whatever way it is spelled**
  (R20, N16's residual): `RENAME TABLE IF EXISTS`, `WAIT n`/`NOWAIT`,
  comments before the verb — the gh-ost cut-over included.
- **A key twin lists every warning before it allows 1062** (R17): a window
  with more case- or pad-only key collisions than `max_error_count` no
  longer refuses every rerun.
- **A 0.62.0 residue journal key is used only by its own first window**
  (R16): the legacy fallback stops at the first residue window, closing
  D10 for upgraded tables.
- **A tracked table renamed away is refused, not dropped as untracked**
  (R13); **a generated column the WAL cannot carry is refused** (R21);
  **a binary session that meets a historic column type drains on text**
  (D15's retry).
- **`github+api` hardening** (R22-era): owner and repo must be GitHub
  names, `APITAP_GITHUB_API` sets an Enterprise API root, a crawl survives
  an issue updated mid-read.
- **Postgres ALWAYS identities are never SET and VIRTUAL columns are
  never written** (R25); **a NUMERIC wider than 76 digits reads as text,
  never as a tiny float** (R32); **an append over an all-NULL cursor is
  refused, not copy-everything** (R12); **a MySQL replace refuses only
  what the user added**, never apitap's own key or the server's defaults
  (R10/R11); **a CDC bootstrap orders by a key with any legal name**
  (D16's regression); **a ch → ch Nullable source column the sink makes
  non-Nullable is cast** (R5/R28/R31).

## The residuals the wave left, closed here

- **A masked readback takes the newest live version** (N2's finding 4).
  FINAL collapses by the sorting key, not the key the readback asks for,
  so a 0.62.x apply on a tombstone-shaped table whose ORDER BY is not the
  key can have left one key live twice — both rows came back and
  `lines().next()` took whichever part the scan reached first, a coin
  flip that could re-land the stale value of an untouched TOAST column.
  Both residue readbacks now say which row they want
  (`ORDER BY _apitap_ver DESC LIMIT 1`), and the apply's key-wide DELETE
  sweeps the duplicate on its way — the key leaves the window once.
- **A slots=N retry's bootstrap plans its share of the cage** (D18's
  finding 1). The bootstrap turn makes a first slots run safe by
  construction; a retry is not that shape — one group re-bootstraps at
  the full single-table plan while its N−1 siblings drain beside it in
  the same process. The nested load now divides its memory plan by
  1 + the groups of this process on the drain side, read per table after
  the turn: first runs read 0 (the siblings are parked on the turn) and
  keep the full plan, so no measured number regresses. The share is
  priced by the same planner (`knobs_denom`), never a magic number.
- **The FK-cascade refusal's remedy says to re-bootstrap** (N17's finding
  6) and names where the mid-run gap itself closes; **the changelog
  rebuild's retired-table drops go through `drop_own`** (D20's finding 3),
  so a big retired table does not wait for the next run's sweep.

## The regression the wave brought, caught by the gate

The wave's server-identity check (`18f22df`) read the marker state row
before the MySQL lane's `resolve_names`, so every MySQL → Postgres
log_based run of a bare-named table panicked at
`parts_of`'s debug assert — `PanicException: lease key before
resolve_names` — on the two gate legs that reach that lane. Located by
rerunning the leg's warm-up with `RUST_BACKTRACE` on the rig;
`resolve_names` now runs above the check, where the members are final.

## One-shot MySQL drains wait out transactions with nothing for us (R18)

The window deadline waited for the end of a transaction only when it had
buffered tracked rows: inside an untracked one (a retention DELETE, a
staging LOAD) the buffer stayed empty, the deadline broke mid-stream with
nothing gained, and every scheduled run re-read the same bytes while the
tracked tables' changes sat behind them — on green runs. The deadline and
SIGTERM now wait for the end of ANY transaction (`in_tx` spans BEGIN and
MariaDB's GTID start through XID, ROLLBACK, a MyISAM COMMIT and every
DDL's implicit commit). `APITAP_MY_WINDOW_SECS` (default 30) replaces the
one-shot drain's hardcoded window seconds. The leg streams a 1 GB
untracked transaction past a 1 s deadline: measured on the rig, the
drain is single-threaded at ~0.93 core and ~44 MiB peak, and in the
0.5 CPU / 256 MB production cage the punch-through runs 7.8 s with the
tracked row landing on the next run.

## The gate, and what it took to trust it

The release is the first gated on five preview runs of the rig: every
failure across them was explained, and two of them changed the tree —
the panic above, and the leg hardening below. Four legs are new
(`e2e_my_deadline_untracked_tx`, `e2e_ch_legacy_dup_readback`,
`e2e_slots_retry_budget`, `e2e_ch_legacy_tuple_engine` — 223 total), and
three legs were de-flaked by the same lesson: an overlap leg's load must
outlast the other run's startup and scan, deterministically by size, not
by a timer (`concurrent_runs` 1+2/5/6 at 2M rows), and a rig-fact
failure carries the evidence instead of a guess (`worker_cancel` prints
the child's stderr when its pipes never opened).
