# 0.65.0: BigQuery lands what the source holds

0.65.0 closes the BigQuery items the deep reviews left open (D3, D4, D8,
D19, N19, R22). Along the way it fixes three type mappings that lost or
reshaped data with every run green. It also fixes one latent CDC bug that a
new leg found on its first run. Every fix has a leg that was run RED on
0.64.0 and green here, on live BigQuery.

## Upgrade notes (read this one)

**Column types change for new tables and for `mode="replace"`.**

| source column | 0.64.0 landed | 0.65.0 lands |
|---|---|---|
| Postgres `boolean`, MySQL bool | INT64 1/0 on the text lane | `BOOL` on both lanes |
| Postgres `bytea` | STRING holding `\x`-hex text | `BYTES`, the source's bytes |
| MySQL `binary`/`varbinary`/`*blob`/`bit` | refused on the binary lane, STRING otherwise | `BYTES` |
| Postgres `numeric` with no precision | FLOAT64, **rounded** (`99999999999999999.99` → `1e+17`) | `BIGNUMERIC`, exact |

**Existing targets keep their type.** An `append`, `merge` or CDC window
into a table an older release created goes on writing the old type: INT64
1/0, STRING hex text, FLOAT64. Nothing is altered in place. Run the table
once with `mode="replace"`, or re-bootstrap the CDC lane, to move it to the
new type. A legacy INT64-bool target on the parquet lane (pipes ≥ 4) is
refused with that remedy, because parquet cannot write the old shape.

Queries that read these columns with the old type, such as `flag = 1` or
`SUBSTR(b, 3)`, need changing after the replace.

## The findings

- **D3: the readback reads every page.** `jobs.query` returns about 10 MB
  per page. 0.64.0 read only the first page, so a masked-row readback
  bigger than that saw only part of the target. The readback now follows
  every `pageToken`, waits out `jobComplete`, and refuses a short read
  (`rows ≠ totalRows`). (`e2e_bq_readback_pages`)
- **D4: an empty CDC bootstrap publishes its table.** A source table with
  no rows bootstrapped to no BigQuery table at all, while the watermark was
  still stamped. Every later window then failed on "target ... does not
  exist", forever. A re-bootstrap after the source was emptied kept the
  old destination rows. The bootstrap now publishes the empty, typed
  target and its state, and the re-bootstrap empties the destination.
  (`e2e_bq_empty_bootstrap`)
- **D8: MySQL binary cells land as their bytes.** The binlog ships raw
  bytes. They are now staged as `\x`-hex, which the BYTES cast and the
  readback both read. 0.64.0 could not reach this code, because its
  bootstrap refused MySQL binary columns into BigQuery. 0.65.0 opens that
  lane, so the fix ships with it. (`e2e_my_cdc_dests bq`)
- **D19: state rows no longer spend the table's load-job quota.** Every
  table of a dataset writes into one `_apitap_state`, and BigQuery allows
  1,500 load/copy modifications per table per day. 70 tables synced hourly
  ran out by the evening. State rows now go in as one DML `INSERT`, which
  is not counted. The sandbox refuses DML, so there the write falls back
  to the load. (`e2e_bq_state_dml` asks `JOBS_BY_USER`: 0 load jobs on
  `_apitap_state` across two 12-table runs.)
- **N19: a bool is BOOL on both lanes.** (`e2e_bq_bool_lanes`)
- **R22: a FLOAT64 key no longer fails the bootstrap.** BigQuery cannot
  cluster on FLOAT64 or partition a window by it.
  - A `changelog=True` bootstrap on a float key failed at any size.
  - A replica keyed `(float8, int)` failed at 1M rows, and every rerun
    repeated the full load before failing again.
  - Clustering now skips the keys BigQuery refuses.
  - `__current` partitions a float key by its round-trip text.
  - An explicit `order_by` naming a float column is refused, naming the
    column and its type.

  (`e2e_bq_cluster_keys`)

## Bytes and big numerics

- **bytea and MySQL binary columns land as `BYTES` on both lanes.** On the
  text lane, the `\x`-hex is turned into the base64 that BigQuery's CSV
  reader takes. The binary (parquet) lane writes the bytes directly. The
  values tested include NUL, 0xFF, a backslash, `\x` spelled inside a
  value, invalid UTF-8, the empty value and NULL. (`e2e_bq_bytes`)
- **An unconstrained numeric lands as `BIGNUMERIC`.** The decimal text
  travels unchanged and BigQuery parses it. A value past BIGNUMERIC's 38
  fractional digits is refused by the load, never rounded.
  (`e2e_bq_numeric`)

## The bug the new leg found: a column named `t`

The CDC MERGE named its tables `T`, `S` and `F`. BigQuery resolves a bare
`t` in `UPDATE SET t = …` to the alias, case-insensitively, and refused:

    UPDATE ... SET does not support updating the entire row

So every window of a table with a column named `t` failed, from the first
BigQuery CDC release on. The aliases are now `_apitap_t`, `_apitap_s` and
`_apitap_f`, the same convention `__current` already used. A source column
with one of those names is refused up front. The new MySQL → BigQuery leg
has a column `t`; it went RED on its first gate run and green with the fix.

## DuckDB reads `apitap.read()` directly

The README has long said DuckDB could read an `apitap.read()` reader with no
copy. It could not. DuckDB binds a PyCapsule object by its schema before it
scans it. With only `__arrow_c_stream__` on the reader, DuckDB opened the
stream twice, once for the schema and once for the scan, and apitap's
one-shot stream refused the second open:

    RuntimeError: read stream already consumed

The only way round it was wrapping each reader in pyarrow. The reader now
exports `__arrow_c_schema__` natively, from Rust (`get_schema` of the stream
it still owns, no stream opened, no pyarrow). DuckDB asks for the schema,
then opens each stream once. A join across two databases is now one SQL
statement over two streams, with nothing landed first:

```python
con = duckdb.connect(config={"memory_limit": "120MB", "threads": 1})
li = apitap.read(PG, table="lineitem", columns=[...])
od = apitap.read(MY, table="orders", columns=[...])
con.sql("SELECT ... FROM li JOIN od ON l_orderkey = o_orderkey ... GROUP BY 1")
```

(`e2e_read_duckdb`: a Postgres and a MySQL table joined and aggregated in
DuckDB, equal to the answer computed from each server's own text, pyarrow
made unimportable; RED on the first 0.65.0 build with the error above.)
