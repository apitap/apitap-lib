# 0.62.1: a ClickHouse CDC replay no longer loses an update

One fix on top of 0.62.0: deep review D10, which the 0.62.0 notes listed as
open. Upgrade if ClickHouse is a log_based destination of yours.

## What was wrong

A masked update (an UPDATE that leaves a TOASTed column unchanged) on
ClickHouse is readback → DELETE → INSERT. The patched image is journalled
first, so a run that dies between the DELETE and the INSERT can re-land it
(M-13). The journal named each op by its ordinal among the window's ops on
that key.

A replay can end sooner than the attempt that died: a smaller budget, a
deadline, a SIGTERM. It commits early, and the next window starts counting
inside the dead attempt's range. There, `1|k` named a different op, and the
window applied that op's image instead of its own. The run exited 0, and the
destination kept the older value: a silent lost update.

On an insert-only (`ReplacingMergeTree`) table, a reused image also carried
the dead attempt's `_apitap_ver`, which could outrank a later write under
FINAL.

## The fix

- Both CDC lanes stamp each residue op with its transaction's commit
  position: the Postgres commit `end_lsn`, or the MySQL/MariaDB position
  after the commit event.
- A journal entry is keyed `position|n|key` and versioned by that position.
  It is reused only by the op it was written for, wherever the window
  boundaries fall.
- The journal holds the image without its version. An insert-only image
  takes the applying window's `_apitap_ver`.
- `APITAP_DEBUG=1` now traces the ClickHouse residue apply: each window, each
  op's journal key, and every journal hit, miss and write.

Upgrade note: a journal row that 0.62.0 left after a crash mid-residue uses
the old key and is never reused. That op reads its row back, as a first
attempt would. If 0.62.0 died between that op's DELETE and INSERT, the run
stops with "row missing … not in the residue journal" instead of guessing.

## Proof

`benchmarks/e2e_ch_journal_window.py` (pg → ch):

1. T1 masks id=1 to 'a', T2 is a >1 MiB filler, and T3 masks id=1 to 'b'.
2. Attempt A drains all three and is cut after journalling T1, between its
   DELETE and INSERT. The leg checks that the journal row exists on the
   server.
3. The replay runs with a 1 MiB budget, so T1 and T3 land in two windows.
   The leg checks that split in the trace.
4. The destination must equal the source.

On 0.62.0: `lost update: id=1 is 'a' at the destination, 'b' at the source`.
On 0.62.1 it passes.

The first version of this leg stayed green on the buggy build. The traces
showed why: its proxy cut a set-phase INSERT, before any journal row existed,
so the journal was never read. The leg now arms on the journal write.

## Gate

`python3 benchmarks/gate.py` on the release wheel below, from `62e161e`, with
the 0.55.1 and 0.56.0 rolling-upgrade legs and the GTID MySQL leg enabled:

- **150 passed, 1 failed, 17 skipped** of 168 legs, in 3139 s. 208 claim cells
  touched; **0 GAP** cells in the whole matrix.
- All 17 skips are BigQuery (`needs bq`).
- The failure is `e2e_worker_cancel.py my`, check F2: the source read 2,581,817
  of 4,000,000 tuples, against a bound of 2,000,000. Every other check in it
  passed (no COPY left, no artifact, every KILL QUERY accepted, a re-run lands
  the table).
  - In that run the first terminated COPY did not make the child raise within
    10 s, so the leg killed a second backend while the other workers kept
    reading. The leg's own comment describes this race: a connection killed
    between spans is replaced by the pool.
  - Rerun alone on this exact wheel, it passed 3 out of 3 (one kill each;
    616,675 to 1,134,975 tuples read).
  - Nothing this release changes is on that path: every engine change since
    0.62.0 is under `logbased/` (CDC), and the leg is a bulk pg → mysql
    transfer.
- An earlier QA-build gate of the same code had one other failure:
  `e2e_my_lower_case_names` queried the leg's throwaway MySQL during the
  image's init restart (ERROR 2002). The leg now waits over TCP (`750b250`).
  In this gate it passed.
- 557 unit tests pass; `cargo fmt` is clean.
